### Fixed

- A flex item told to ignore its own content took its size from the content
  anyway. A panel beside a fixed-height sibling came out at its content's
  height rather than the sibling's, so a 1024-tall image or a long block of
  text in a `flexGrow: 1` column pushed the whole row to 1024 where a browser
  gives 200.

  `flexBasis` with a minimum is what CSS provides for saying _ignore my
  content, take your size from the line_, and it now does that here. Both parts
  are needed and neither is enough alone: an automatic minimum floors the item
  at its content whatever the basis says.

  **Neither value has to be zero.** `flexBasis: 0` with `minHeight: 0` is the
  spelling most people write, but `flexBasis: 1`, `flexBasis: 120` and
  `minHeight: 1` collapse the same way, and so does `minHeight: '0%'`. What
  does not collapse is `flexBasis: '0%'` — a percentage basis against a
  container with no height of its own means _auto_, so the content decides, and
  a browser agrees.

  A container with a stated height was never affected, which is why this
  survived: give the column a `height` and the same declarations always worked.

  **This is compensation for the layout engine underneath rather than a fix in
  it**, and it is marked as such in the source. That engine builds a flex
  container's content size from what its items contain rather than from the
  sizes those items asked for; this renderer supplies the right number before
  the solve. It carries a probe pinned to what the engine does today, which
  fails on the day it stops needing one — so this behaviour can move again,
  toward the browser. **No upstream issue covers this one**, so there is no
  number to watch, and the issue this repository filed stays open until the
  engine is fixed, by design rather than by oversight. (#145)
