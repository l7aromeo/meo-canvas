The first stable release of this renderer, and the first thing a `latest`
consumer has seen since `9.0.4`. It is a second generation rather than a version
bump: the renderer underneath is new, the surface is deliberately v9's, and
where the two disagreed the behaviour is now the browser's.

**Read the crossing before anything else.** It is what a caller on `9.0.4` has
to change, measured against the `v9` branch rather than recalled.

### Added

- **A new renderer behind the same surface.** Describe a picture; get image
  bytes back. Layout is CSS flexbox, grid and block; drawing is Skia; text is
  shaped and broken here rather than handed to a canvas, which is what makes a
  paragraph behave like a browser's. The property names, the node factories and
  the output methods are v9's, so a ported script changes syntax rather than
  design.

- **Behaviour is measured in Chrome, not read from a specification.** Where a
  question has a CSS answer, the answer is what a browser does. That is the rule
  the comparison tables in this repository exist to hold, and it is why some v9
  shapes render differently here — `z-index` follows CSS's rule for positioned,
  flex and grid children rather than v9's narrower one, and an image with no
  size of its own keeps its own dimensions rather than being sized by its
  surroundings.

- **Diagnostics.** A value the renderer could not use no longer fails the render
  and no longer disappears: `canvas.diagnostics` reports it alongside the
  picture, because a markup tag with an unusable colour should still draw its
  text. Each one names the path it is about — the tag as written, value
  included, so `<color=zzz>` is distinguishable from `<weight=1500>` — and
  carries the byte offset into the markup, which tells three `<color>` tags in
  one string apart. Every diagnostic raised today is a markup tag. v9 had no
  channel for this: an unusable value was either fatal or silent.

- **The canvas is retained, and encoding is separate from rendering.** `Root`
  returns a handle to a painted surface; `toBuffer` encodes that surface again
  at a different format rather than re-rendering it. Two formats of one picture
  cost one layout and one paint. The asynchronous forms hand the encode to a
  worker pool and the loop stays free — at 4000x4000 the record costs 2.74 ms
  and the encode 97.23 ms, so nearly all of it is on the far side of that line.

- **Twelve encodings**: png, jpg, webp, avif, tiff, bmp, ico, svg, pdf, gif,
  apng and raw bytes. Several pages become frames in gif, apng, webp and avif,
  sheets in pdf and tiff, and sizes in ico.

- **A page as tall as its content.** Omit `height` and the content decides it;
  `minHeight` then travels as the page's floor, so "at least this tall" is
  expressible without a second flag. `width` has no such form and cannot — text
  breaks into lines against a width, so a width has to be known before anything
  can be measured, where a height is a consequence of that measuring.

- **One binary per platform, fetched rather than bundled.** The addon does not
  ship inside the package: `optionalDependencies` names one platform package per
  target, so an install pulls the binary for the host instead of seven. No
  postinstall script, so offline installs, locked-down CI and `--ignore-scripts`
  all work.

### Crossing from 9.x

**The API is v9's on purpose** — `Root`, `Row`, `Column`, `Box`, `Text`, flat
style props, and the same output methods. A ported script should be changing
syntax, not a design. Six things do not mean here what they said there, and
they are listed with what each costs when missed, because that decides how much
of a port has to be re-checked.

- **A bare `Box` runs the other way.** v9's direction is Yoga's `column`; this
  follows CSS and is `row`. Write the axis out on every container. The shrink
  looks like a second trap and is not: v9's constructors all declare
  `flexShrink: 1`, which is already CSS's value, so a faithful port writes no
  `flexShrink` at all — writing `0` is a divergence dressed as a reproduction.
- **`lineHeight` is a different quantity.** v9's is the line box in **pixels**;
  here it is a **multiple of the em size**. `lineHeight: 24` at `fontSize: 18`
  is 24 pixels there and 432 here. A component written in pixels may still hold
  a bare ratio, and those are the only values that carry over untouched. Wrong
  by a factor of the font size, and it reads as a layout defect rather than a
  unit mistake.
- **Edge groups are gone.** v9 spells `padding: { Horizontal: 2, Bottom: 2 }`;
  here there is only `top`, `right`, `bottom`, `left`. From TypeScript this is
  a compile error. **At runtime it is silent** — a node given
  `padding: { Horizontal: 16 }` renders with no padding and nothing is thrown.
  Port in TypeScript and the whole class is caught.
- **`<b>` inside a plain `Text` is literal text**, where v9 read it as markup.
  `RichText` is the node that parses it. Visible immediately, because the tags
  draw.
- **Capitalisation throughout.** `Style.PositionType.Absolute` becomes
  `'absolute'`, `position: { Top }` becomes `{ top }`. A compile error from
  TypeScript, silently dropped at runtime.
- **`ellipsis` did not change type, and that is worth saying** because an
  earlier draft of the port notes said it had. It takes v9's `boolean | string`
  on both surfaces. `false`, `''` and omitting it all truncate without a marker.

**About half of v9's exported surface has no name here.** Measured against the
`v9` branch rather than recalled, and resolving the two `export *` wildcards in
its `index.ts` — which is where a count goes wrong, because reading that file
alone gives 55 and misses 68 more in `common.const.ts` and `canvas.type.ts`. The
real figures: v9 exports **123** names, this ships **130**, and **63** are
carried over. So 60 v9 names have no counterpart and 67 names here are new.

**Most of the 60 are prop and shape types rather than things you call** —
`BoxProps`, `GridOptions`, `RootPropsWithWorker`, `ChartItem`, `EdgeColors`,
`CornerRadii` and the like. You likely never imported one; a build that did will
not compile. To find out against your own code rather than against a list that
decays, grep your imports from `meo-canvas` and check each name against the
reference for this version.

The ones a caller plausibly reached for:

- **`GridItem` is gone.** A grid item is now an ordinary child carrying
  `gridColumn`, `gridRow` or `gridArea`, so the wrapper disappears rather than
  being renamed. `Grid` itself is unchanged.
- **`terminate` and `WorkerCanvas` are gone**, and nothing replaces them. v9's
  canvas lived in a worker the caller shut down; here `Root` returns a retained
  canvas and the encode is handed to a pool internally. There is no worker to
  terminate and no process left running if you forget.
- **`clearDiskCache` and `setDiskCacheDir` are gone.** There is no disk cache on
  either surface. Decoded images are cached per `Renderer` for the life of the
  process and nothing is written to disk, so a deployment that pointed the cache
  at a writable volume needs nothing in its place.
- **`easings` is now `EASING_NAMES`, and `ease` resolves one.** The rest of the
  animation surface carries over under its own names — `cubicBezier`, `steps`,
  `resolveEasing`, `lerp`, `mapRange`, `interpolate`, `mix`, `spring`,
  `springDuration`, `track`, `sequence`, `parallel` — as do `parseColor`,
  `formatColor`, `mixColor` and `isColor`.
- **`ExportFormat`, `ExportOptions`, `SaveOptions` and `RenderOptions` were
  never this package's types**, which is a different problem from a rename. v9
  re-exported them from `meo-skia-canvas`, so a caller writing
  `import type { ExportOptions } from 'meo-canvas'` was importing another
  package's type through ours. `Format` and `EncodeOptions` here are this
  package's own. The v9 names still exist upstream if you need them.

**The `*Node` type aliases are gone** — `BoxNode`, `ImageNode`, `PathNode`,
`TextNode`, `GridNode`, `GridItemNode`. They named what a factory returned so a
helper could be annotated; the props types (`RootProps` and the per-node prop
types) are what to reach for instead.

**`z-index` follows CSS rather than v9's rule.** v9 applies it only to
absolutely positioned nodes; here a child is stacked by `zIndex` when it is
positioned, **or** when its parent lays out as flex or grid. A static child in
a block container still ignores it.

**`saveAs` is not carried over**, and `toSharp` is absent. `toBuffer`,
`toBufferSync`, `toFile`, `toURL`, `toDataURL` and their sync pairs are all
present, and the sync variants are ordinary functions here rather than
`Atomics.wait` on a worker.

**The addon does not ship inside the package.** One platform package per target
is pulled through `optionalDependencies`, so an install fetches one binary
rather than seven. `darwin-x64` is not among them, deliberately: Apple stopped
supporting Intel and the runner it would need is being retired.

**Node 22 or newer**, declared in `engines`.

**Some of the entries below are workarounds rather than fixes**, and each says so
where it sits — no count here, because a count in prose is a claim nothing
checks and this file grows. The defect is in the layout engine this renderer sits on, and
what ships here is compensation around it — so the issue this repository filed
stays open after the release, by design rather than by oversight, and the entry
cites it anyway.

Two things follow for a caller. A compensation is removed the day the engine
stops needing it, and each is held to that by a test that fails on the day
rather than by anyone remembering — so the behaviour can move again, in the
direction of the browser. And a compensation is narrower than a fix: where one
is known to make some other shape worse, the entry names that shape rather than
leaving it to be met.

### Known limitations

**Some behaviour here is compensation for the layout engine underneath rather
than a fix in it**, and it is marked as such in the source. Each compensation
carries a probe pinned to what that engine does today, which fails on the day it
stops needing one — so the behaviour can move again, toward the browser. The
issues this repository filed stay open until it does:
[`#97`](https://github.com/l7aromeo/meo-canvas/issues/97),
[`#104`](https://github.com/l7aromeo/meo-canvas/issues/104),
[`#107`](https://github.com/l7aromeo/meo-canvas/issues/107) and
[`#123`](https://github.com/l7aromeo/meo-canvas/issues/123). Each names the
shape it does not cover.

**One shape is deliberately not compensated**: a flex item stretched across its
line and then asked for a main size from that stretch comes out `424 x 248`
where a browser gives `424 x 424` — which overflows its own line. Producing an
overflowing box is a layout change nobody asked for, and the upstream proposal
to make it the engine's own answer is open rather than merged.
