### Fixed

- A flex item stretched across its line did not take its main size from its
  aspect ratio. In a column with a height of its own, an item with
  `flexGrow: 1` and `aspectRatio: 1` came out as wide as the line and only as
  tall as the line let it be — `424x248` in a `424x248` content box, where a
  browser makes it `424x424`.

  **The size CSS asks for here overflows its own line**, and that is the
  behaviour rather than a side effect of the repair. A stretched cross size is
  _definite_ (CSS Flexbox 1 §9.8), a definite cross size on an item with a
  ratio becomes the _transferred size suggestion_ (§4.5), and that is the
  item's **minimum** on the main axis — a minimum, so the line cannot clamp it
  back down. Measured against WebKit 26.6, Chromium 153 and Firefox 155: all
  three give `424x424`.

  **Your renders can move, and this is how to keep the old ones.** Add
  `minHeight: 0` to the item. It is not a workaround — the floor is the item's
  _automatic_ minimum, so naming any definite minimum replaces it, and this is
  the spelling CSS provides for the purpose. `height: '100%'` reaches the same
  result for a different reason, since a definite main size leaves nothing to
  derive, and so does `overflow: 'hidden'`, since a scroll container has no
  automatic minimum at all. All three escapes hold the old `424x248`, and hold
  it in every engine.

  **`maxHeight` is the wrong escape, and not because the answer is unsettled.**
  `maxHeight: '100%'` and `maxHeight: 248` both give `424x248` here, which is
  what Chromium and Firefox give and what the specification's own wording gives
  — the minimum is "clamped by the maximum main size if it's definite", which
  bounds the height and says nothing about the width. **WebKit is the one that
  differs**, taking the clamped height back through the ratio to `248x248`. So
  a render written that way holds here, in Chrome and in Firefox, and moves in
  Safari; `minHeight: 0` holds in all of them, which is why it is the one to
  reach for. Both spellings are compared against Chromium like every other row
  rather than exempted from comparison, so this is a behaviour under test
  rather than a claim in a note.

  **And these renders moved too.** An item already carrying `maxHeight` came
  out `248x248` in `10.0.1` and comes out `424x248` here. The clamp holds the
  height where it always did; the width it used to shrink to was this same
  defect seen from the other side.

  **A second family moved, and it moves the other way.** Where the shape above
  gains height, these had their **cross** size derived from the main one rather
  than set by the stretch, so they come out narrower: `aspectRatio: 2` was
  `496x248` and is `424x248`, and an item whose content is taller than the
  ratio's answer was `600x600` and is `424x600`. The `maxHeight` rows above are
  the third member of it.

  **Twelve rows across the conformance tables move between `10.0.1` and
  `10.0.2`**, and the rest are the first shape under other spellings:
  `flexGrow: 0`, padding, `boxSizing: 'border-box'`, two stretched items
  sharing a line — `424x124` to `424x424` — and `aspectRatio: 0.5`, which goes
  `424x248` to `424x848`.

  **This is compensation for the layout engine underneath rather than a fix in
  it**, and it is marked as such in the source. That engine does not give a
  stretched item the minimum its ratio owes it, and this renderer supplies it
  before the solve. It carries a probe pinned to what the engine does today,
  which fails on the day it stops needing one — so this behaviour can move
  again, toward the browser. The issue this repository filed stays open until
  the engine is fixed, by design rather than by oversight.
