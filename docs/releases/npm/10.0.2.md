### Fixed

- A flex item stretched across its line did not take its main size from its
  aspect ratio. In a column with a height of its own, an item with
  `flexGrow: 1` and `aspectRatio: 1` came out as wide as the line and only as
  tall as the line let it be — `424x248` in a `424x248` content box, where a
  browser makes it `424x424`.

  **The size CSS asks for here overflows its own line**, and that is the
  behaviour rather than a side effect of the repair. A stretched cross size is
  _definite_ (CSS Flexbox 1 §9.8), a definite cross size on an item with a
  ratio becomes the _transferred size suggestion_ (§4.5), and that is the
  item's **minimum** on the main axis — a minimum, so the line cannot clamp it
  back down. Measured against WebKit 26.6, Chromium 153 and Firefox 155: all
  three give `424x424`.

  **Your renders can move, and this is how to keep the old ones.** Add
  `minHeight: 0` to the item. It is not a workaround — the floor is the item's
  _automatic_ minimum, so naming any definite minimum replaces it, and this is
  the spelling CSS provides for the purpose. `height: '100%'` reaches the same
  result for a different reason, since a definite main size leaves nothing to
  derive, and so does `overflow: 'hidden'`, since a scroll container has no
  automatic minimum at all. All three give `424x248` in every engine.

  **Do not reach for `maxHeight`.** It is the obvious clamp and the three
  engines do not agree on it: `maxHeight: '100%'` and `maxHeight: 248` both
  give `424x248` in Chromium and Firefox and `248x248` in WebKit, because
  WebKit takes the clamped height back through the ratio and the other two do
  not. This renderer follows Chromium and Firefox there, which is also what the
  specification's own wording gives — the minimum is "clamped by the maximum
  main size if it's definite", which bounds the height and says nothing about
  the width. It is recorded as a disagreement rather than compensated.

  Three more things moved with it, all in the same direction: an item with
  `aspectRatio: 2`, an item whose content is taller than the ratio's answer,
  and two stretched items sharing a line each had their **cross** size derived
  from the main one where the stretch should have set it.

  **This is compensation for the layout engine underneath rather than a fix in
  it**, and it is marked as such in the source. That engine does not give a
  stretched item the minimum its ratio owes it, and this renderer supplies it
  before the solve. It carries a probe pinned to what the engine does today,
  which fails on the day it stops needing one — so this behaviour can move
  again, toward the browser. The issue this repository filed stays open until
  the engine is fixed, by design rather than by oversight.
