### Added

- `frame` takes a negative index, counting from the end: `.frame(-1)` draws the last frame of an animated image and `.frame(-2)` the one before it. A source with one frame ignores a negative index as it does a positive one.

- `justify_items` and `justify_self` place a grid item or a block child along the inline axis with every value CSS gives them, on `Style` and `LayoutStyle`, as the `JustifyItems` and `JustifySelf` enums over `SelfPosition`, `OverflowPosition` and `LegacyPosition`: `normal`, `stretch`, `baseline` (one variant for CSS's `baseline` and `first baseline`) and `last baseline`, the nine positions `center`, `start`, `end`, `self-start`, `self-end`, `flex-start`, `flex-end`, `left` and `right`, each with or without `safe` or `unsafe`, and on `justify_items` `legacy left`, `legacy right` and `legacy center`. `justify_self: None` is CSS's `auto` and `justify_items: None` its initial `legacy`, which takes an ancestor's `legacy` position through boxes stating nothing. A grid column's items asking for `baseline` or `last baseline` align their left border edges at its start or end, as Chrome does, and a flex item ignores both properties. `anchor-center` has no variant, since a scene has no anchor positioning. `LayoutResult::inherited` reports what each node took from its ancestors (`l7aromeo/meo-canvas#171`).

- `Measure::has_picture`, a provided method a measurer answers for an image leaf: whether its source decoded. Layout lays an image without a picture out as Chrome lays out a broken `<img>` with no `alt`, a box around a 16px icon rather than a replaced element. It defaults to `true`, so a measurer that loads no images keeps every image's layout as it was (`l7aromeo/meo-canvas#183`).

### Changed

- **Breaking.** `Style::frame`, the `frame` setter and `NodeKind::Image::frame` take an `i32` rather than a `u32`, so that a negative index can count from the end. An integer literal compiles unchanged; a `u32` value needs converting, for example with `i32::try_from`.

- **Breaking.** The scene file format is version 10, and a `.mcs` file written by 0.1.x is refused with `CodecError::UnsupportedVersion` ("scene format version 7, expected 10"). Re-encode the scene with this release.

- The page root's background colour fills the whole canvas beneath every effect the root carries, as the root element's does in Chrome: a root with `opacity` below 1, a `mask` or a `border_radius` draws its colour opaque and out to the canvas's corners, with its content, gradient and image over it. Its `filter` applies to the whole canvas; its border and shadows stay on its box.

- A frame index past either end of an animated image is refused as `Error::FrameOutOfRange`, naming the index as written and the frame count ("node N asks for frame F of an image with M frames"), rather than as `Error::UndecodableImage`.

- Building from source on x86_64 needs `yasm`, or `nasm` older than 3, for libaom: libaom 3.11 refuses the nasm 3.01 that Ubuntu 26.04 ships, with "Unsupported nasm: multipass optimization not supported". `cmake` is still needed as before.

- The `net` feature builds `rustls` without its default features, so `aws-lc-rs` and `aws-lc-sys` are no longer compiled: 0.1.4 took `rustls`'s defaults, which select the aws-lc-rs provider and turn on `prefer-post-quantum`, while `ureq` speaks TLS through ring. ring is the only provider compiled.

- Crate releases are tagged `crates-v<version>` from this release on, so its GitHub release page is `releases/tag/crates-v<version>`. Earlier releases keep their `rust-v` tags and pages.

- **Breaking.** `LayoutStyle::direction` is an `Option<Direction>`, `None` by default: an unset direction inherits from the nearest ancestor that states one, which an explicit `Direction::Ltr` under an `rtl` parent does not. Code that set it writes `Some(Direction::Rtl)`; code that read it reads `LayoutResult::direction(node)` for the direction a node was laid out in.

- **Breaking.** `layout::to_taffy_style` takes a `layout::Inherited` as a third argument, built with `Inherited::new(direction)`: the node's resolved direction, its alignment container's, and the `legacy` an unset `justify_items` takes, none of which its `LayoutStyle` alone can say. `LayoutResult::inherited` is that value for a solved node. It returns taffy 0.15's `Style`, since `meo-canvas-core` depends on `taffy` `0.15` rather than `0.14`, so a caller handing the result to its own taffy tree moves to taffy 0.15, where `align_items`, `justify_items`, `align_content` and `justify_content` are no longer `Option`s and `normal` is `AlignItems::NORMAL` rather than `None`.

- **Breaking.** `Style` and `LayoutStyle` gain the public fields `justify_items` and `justify_self`. Both structs are exhaustive by design, so a struct literal naming every field without `..` no longer compiles; add the two fields, or close the literal with `..Style::default()` or `..LayoutStyle::default()`.

- An image whose source cannot be fetched or decoded takes the box Chrome gives a broken `<img>` with no `alt`, rather than collapsing on every axis it does not size. With only a width it was that wide and 0 tall, so its placeholder drew nothing; an `auto` axis nothing stretches is 16 instead, so `Image::url(…)` given `.width(px(100.0))` is 100x16, and as a block child or a stretched grid or flex item it fills its container (300x16 in a 300-wide block, the whole cell in a grid) as Chrome's does. It is laid out in that box under every `OnImageError`, and an image with both sizes stated is unchanged (`l7aromeo/meo-canvas#183`).

- A colour tween with a translucent end follows Chrome: `animate::color::mix`, and every track, keyframe sequence and spring carrying an `Rgba`, mix with the alpha multiplied in, as Chrome mixes a CSS animation or transition of a colour. `rgba(255, 0, 0, 0)` to blue at halfway is blue at half alpha where it was a purple, `Rgba { r: 127.5, g: 0.0, b: 127.5, a: 0.5 }`, and red to blue at 0.2 alpha at halfway is red 212.5, blue 42.5 at 0.6 where it was 127.5 and 127.5. A tween between two opaque colours is unchanged, to the bit, and two transparent ends still mix their hues straight (`l7aromeo/meo-canvas#208`).

### Fixed

- A text item that wraps is as wide as the space it is offered, as in Chrome, rather than as wide as its widest line, wherever it is not stretched: in a flex column under `Align::FlexStart` or `Align::Center`, and in a container sized to its content, such as an absolutely positioned box with only a `max_width`. In a 200-wide column with 50 of horizontal margin it was 137 wide where Chrome gives 150. Right- and centre-aligned lines move with the box, and an item cut to one line by `max_lines` is the full 150 rather than 134. Stretched items, rows and blocks were already right (`l7aromeo/meo-canvas#162`).

- **`--features net` builds of `meo-canvas-cli` refused URL images.** The feature compiled an HTTP client the binary never called and left fetching off in `meo-canvas-core`, so every `ImageSource::Url` failed as though the feature were absent, and in exactly that build the message dropped its hint to build with `--features net`. The feature enables the core's fetch, so a URL image is fetched. A fetch that fails, under `on_image_error: Throw`, exits 6, source unobtainable, and names the URL.

- With the `net` feature, an image URL whose host does not resolve is reported as `FetchFailure::HostNotFound` (do not retry) rather than `FetchFailure::Transport` (retry), in `Error::SourceFetch` and in `ImageWarning` alike. A lookup that could not finish, because the resolver was unreachable or said to try again, stays `Transport`.

- An SVG image given `frame(1)` or later draws, as a still raster does, rather than being refused as `Error::UndecodableImage`.

- The page root's `margin` and `position` place it as Chrome places `<html>`, rather than being ignored: an unsized root fills the canvas less its margins, a percentage resolving against the canvas width on either axis, `Dimension::Auto` counting as no margin and a negative margin growing it; under `PositionType::Relative`, a `position` offset moves it without resizing it, while a root left `Static`, the default, ignores its offset as a static box does; and a page as tall as its content counts the root's vertical margins. Its background still covers the whole canvas, its gradient and image tiling from the root's box. A stated size is still the canvas size.

- An `Image` grid item under the default alignment draws at its intrinsic size, as Chrome does, rather than stretched to fill its cell. `.align_items(Align::Stretch)` still stretches it, its width following its ratio.

- A `Transform`'s translation is applied after its rotation and scale, as CSS applies `translate` after `rotate` and `scale`, rather than being rotated and scaled with the box. A box translated 20px and scaled 2 moves 20px, not 40px, and a 20px box at the page's top-left corner, translated 20px and turned 90° about that corner, covers x 0 to 19 rather than leaving the canvas. A transform with only a translation, or none, draws as before (`l7aromeo/meo-canvas#166`).

- The CLI README's usage line omitted the `render` subcommand, so the command it showed was rejected with "unrecognized subcommand".

- **`meo-canvas` exited 0 with nothing on stderr when an image URL could not be obtained.** A dead URL in a `net` build, or a failed fetch the scene recorded, was drawn as a placeholder, or as nothing, and no trace of it reached the caller. Each such source prints one line on stderr, `meo-canvas: warning: node=… nodes=… failure=… url=… detail=…`, with `status=…` after `failure=status`; the exit code stays 0. The URL is written with space, tab, CR and LF percent-encoded (`%20`, `%09`, `%0D`, `%0A`), so every field before `detail` is one token: split on spaces up to `detail=`, and the rest of the line is the detail, its CR and LF written as spaces. The CLI README documents the fields.

- **A box that states no `direction` takes its parent's, as it does in Chrome.** Under an `rtl` page a grid with no direction of its own ran its tracks from the left, a flex row put its first item at the left, a block's child under a box stating no direction sat at the left edge, and a line's `TextAlign::Start` and `TextAlign::End` aligned as under `ltr`. Each follows the nearest ancestor that states a direction, along the scene's tree even for a box placed against another one, and an explicit direction still overrides it (`l7aromeo/meo-canvas#165`).

- A wrapped text box draws the lines its layout measured. Layout lays text out at a fractional width and rounds the box to whole pixels, and the text was then wrapped again at the rounded width, so a paragraph given `width(px(137.2))` with a line just over 137 wide drew a third line below its two-line, 48-tall box; it draws two, as Chrome does. A box less than a pixel narrower than its text, such as a label 82.14 wide at `width(px(82.0))`, breaks it, as Chrome does, rather than drawing one line wider than the box. `LayoutResult::wrap_width` is the unrounded width each leaf was laid out at.

- The API reference described two items wrongly. `pie` said it draws a doughnut when `inner_fraction` is above zero; it never reads the option, and `doughnut` is the chart with a hole. `Align::Baseline` said a measured text leaf aligns on its bottom edge; it aligns on its text's first baseline, offset by its own top padding and border.

- An `Image` draws its picture where Chrome draws it when the box or the fit falls between pixels: the picture is fitted in the box as laid out, before it was rounded, and each of its edges is snapped to a whole pixel, a half rounding up. A namecard picture of 840x400 in a box 350 wide and 166.67 tall was scaled under `ObjectFit::Cover` from the 167-tall rounded box, 350.7 wide and a third of a pixel to the left, so it differed from `ObjectFit::Fill` across the whole box by up to 29 per channel; the two are the same picture, as in Chrome. `Contain`, `None` and `ScaleDown` that leave an odd free space, such as `Contain` at 16.5 in a 333x150 box, draw from the next whole pixel rather than across two. An SVG source under `Fill` in a box of another aspect lays its drawing out under its own `meet` inside the box, and that drawing is snapped in the same way. (`l7aromeo/meo-canvas#185`).

- A `Path` with a `view_box` is fitted into its content box, inside its padding and border, as Chrome maps an `<svg>`'s `viewBox`, and at the box's size before rounding. With 7px of padding and a 3px border it drew across the whole box, 8px outside Chrome's drawing at the sides and the top; in a box 166.67 tall it was scaled as though 167, which moved a point ten times the `view_box`'s height down by 3.4px (`l7aromeo/meo-canvas#185`).

- An `Image` in block flow keeps a declared height, and a `max_height`, below the height its picture's aspect ratio would give its width, as Chrome does: one 200 wide over 60x40 art with `height(px(60.0))` or `max_height(px(60.0))` was laid out 133 tall, the ratio's height, where Chrome gives 60. A `min_height` above that maximum still wins over it. A flex container was already right, and so was a declared height above the ratio's. The same held for any node without children that has an `aspect_ratio`, in block flow (`l7aromeo/meo-canvas#189`).

- A background image lands where Chrome puts it. Along an axis it does not repeat on, its position and its size are each rounded to a whole pixel, a half up, where they were truncated and left fractional: a 300x100 box with `BackgroundSize::PerAxis` of 50% and 25% centred drew its picture from y 37 rather than 38, and a 350x167 one at 62 to 103.72 rather than 63 to 105. Along an axis it repeats on, its phase is no longer truncated: a 33.3-wide tile centred in 300 starts a third of a pixel later, as in Chrome. A tile the box cuts off draws its visible part at the rounded size (`l7aromeo/meo-canvas#186`).

- The API reference described `EncodeOptions::lossless` as WebP's, and every WebP encode given it returns `Error::Encode` with ``invalid `lossless`: webp is either lossless already or has no lossless form``; the CLI's `--lossless` help said the same. `lossless` is AVIF's: `meo-skia-canvas` reads it for AVIF alone and refuses it elsewhere. The reference and the help say so, and say that a lossless WebP is a quality of 1.0, as `meo-skia-canvas` documents (`l7aromeo/meo-canvas#184`).

- An `Image` with a declared width keeps it under a `min_height` whose height its picture's aspect ratio would turn into a wider width, as Chrome does: one 200 wide over 60x40 art with `min_height(px(160.0))` was laid out 240x160, the ratio's width at that height, where Chrome gives 200x160. It held in block flow, as a flex item, in a flex column and out of flow, with a length or a percentage width, as a grid item with a percentage width, and for any node with an `aspect_ratio`. An `Image` with no width still takes its width from the minimum, 240x160, and a `min_width` still wins over the declared width (`l7aromeo/meo-canvas#192`).

- An `Image` with a declared width keeps it under a `max_height` below the height its picture's aspect ratio gives that width, as Chrome does, rather than being narrowed to the ratio's width at the maximum: one 200 wide over 60x40 art with `max_height(px(60.0))` was laid out 90x60 as a flex item, where Chrome gives 200x60. It held as a flex item stretched or not, in a flex column, as a grid item and out of flow, for a percentage width too, and for any node with an `aspect_ratio`, in block flow as well. A growing flex item grows past its declared width, a `max_width` still wins, and an `Image` with no width still takes its width from the maximum (`l7aromeo/meo-canvas#193`).

- An `Image` in block flow with neither a width nor a height takes a `max_height` or a `max_width` through its picture's aspect ratio, as Chrome does: one over 60x40 art with `max_height(px(20.0))` was laid out 60x20, squashed, where Chrome gives 30x20, and with `max_width(px(30.0))`, or a `max_width` of 10% in a 200-wide block, it kept the 40 height where Chrome gives 30x20 and 20x13.33. Padding and `box_sizing` count as in Chrome. Where its bounds disagree, it is sized by CSS 2.2's table for replaced elements, which Chrome follows: a `min_height` of 30 over a `max_height` of 20 gives 45x30, a `max_width` of 30 with a `min_height` of 30 gives 30x30, and a `min_width` of 70 with a `min_height` of 80 gives 120x80 where it was 70x80. A `min_height` or a `min_width` alone was already taken, and so was a `max_height` on an unstretched flex item or out of flow (`l7aromeo/meo-canvas#198`).

- An `Image` flex item with neither a width nor a height keeps its natural size under a `max_height` above its natural height, or a `max_width` above its natural width, in a flex row whose height is not definite, as Chrome does: one over 60x40 art with `max_height(px(60.0))` was laid out 90x60, the size at its maximum, where Chrome gives 60x40, and with a `min_height` of 50 under that maximum it was 90x60 where Chrome gives 75x50. It held for a stretched item, the default, wrapping or not. An item aligned other than `stretch`, a row of definite height and a flex column were already right (`l7aromeo/meo-canvas#197`).

- An `Image` flex item whose declared width is wider than its flex row shrinks to the row, as Chrome does, and its height follows the shrunk width through its picture's aspect ratio: one 300 wide over 60x40 art in a 200-wide row was laid out 300x200, where Chrome gives 200x133.33, and so it was for a 150% width, unstretched, and under a `min_height` the shrunk height exceeds. A `min_height` whose ratio width is wider than the row holds the item at that width, 240x160 under a `min_height` of 160, and a `max_height` bounds the derived height, 200x100 under a `max_height` of 100. Stretched in a row of definite height, it takes that height, 200x100 in a row 100 tall where it was 300x100. A node with an `aspect_ratio` and no picture shrank but kept the height of its declared width, 200x200 where Chrome gives 200x133.33. In a flex column, an `Image` with a declared height taller than the column shrinks to its automatic minimum, the stretched width through the ratio: 150 tall in a column 100 tall it was 200x150, where Chrome gives 200x133.33, and aligned `flex-start` there its width follows the shrunk height, 150x100 where it was 225x100 (`l7aromeo/meo-canvas#196`).

- A gradient stop that is not opaque mixes as Chrome mixes it. A node's `gradient`, the root's included, and `Mask::Gradient` mix with the alpha multiplied in, as CSS specifies: red fading to `Color::TRANSPARENT` or to `Color::rgba(255, 0, 0, 0)` drew a grey band, rgb(191, 129, 129) at the midpoint over white, where Chrome gives rgb(255, 129, 129), and red to blue at 0.2 alpha drew rgb(178, 103, 180) there for Chrome's rgb(229, 103, 128). A `PathPaint::Gradient` fill or stroke mixes straight, as Chrome mixes an SVG gradient, so it is unchanged except that a stop at alpha 0 keeps its own colour: red to `Color::rgba(255, 0, 0, 0)` no longer darkens. Every `ColorType` that keeps colour drew it the same way (`l7aromeo/meo-canvas#202`).

- `Fonts::register_path` and `Fonts::register_bytes`, and `Renderer::register_font` through them, register bytes once per thread: bytes this thread already registered under the family are compared and not registered again, where every call added another copy of the face. A renderer built per render and given the same fonts each time grew memory, by 162 MB over 1,000 renders for one 171 KB face, and on the GPU drew large text one level apart at glyph edges from one render to the next. `Fonts::registered` still lists a family a registry was given whose bytes were already registered (`l7aromeo/meo-canvas#203`).

### Security

- **`ureq` is required at 3.5** under the optional `net` feature, and requires `rustls` at `0.23.46` itself, closing four client-side advisories: an unauthenticated ServerHello downgrading later connections to classical key exchange (`RUSTSEC-2026-0349`), `Debug` output of a client session value exposing its secrets (`-0346`), buffered data sent after an Encrypted Client Hello rejection (`-0347`), and certificate decompression allocating up to 1 GiB before authentication under rustls's `brotli` feature (`-0348`). 0.1.4 required `ureq` 3.4, which requires `rustls` at `^0.23.22`, so a consumer could resolve an affected version even though this repository's lockfile could not.

- **`rustls-webpki` is required at `^0.103.16`** under the `net` feature, closing `RUSTSEC-2026-0382`, certificate verification that could accept a distrusted intermediate: `rustls` requires `^0.103.14`, which admits the affected versions for a consumer. The crate is not imported; the requirement exists to raise that floor. `ureq` 3.5 requires `webpki-roots` at `1.0.10`, closing `RUSTSEC-2026-0381`, bundled roots that let distrusted emSign intermediates be trusted.
