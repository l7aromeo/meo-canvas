# The banner

Four files, one drawing, generated by `tools/brand/banner.mjs`:

| File                | What it is                     | Used by                               |
| ------------------- | ------------------------------ | ------------------------------------- |
| `banner-dark.webp`  | animated, dark palette         | GitHub, `prefers-color-scheme: dark`  |
| `banner-light.webp` | animated, light palette        | GitHub, `prefers-color-scheme: light` |
| `banner.webp`       | animated, theme-neutral        | npm and crates.io, and the fallback   |
| `banner.png`        | the first frame, theme-neutral | anywhere that will not animate        |

1280×468, 60 frames, two seconds at 30fps.

Regenerate with `just brand`, and commit what it writes.

## Why it shows what it shows

**It is drawn by meo-canvas, so it is proof rather than illustration.** If
layout, text shaping, gradients, shadows, paths or the easing catalogue break,
the banner breaks with them — and it is the only thing here that exercises the
animated-encode path at this frame count and size.

What it draws is the thing this library is unusual for: **it computes motion.**
Four cards, each drawing one curve from the catalogue as a stroked path, with a
dot running that curve and a bar reading the same number a second way. The four
span the kinds rather than looking different — a plain ease-out, one that
overshoots at both ends, one built from segments, and a spring that is
integrated rather than evaluated. That is the whole animation surface in one
picture.

The motion is a triangle rather than a sawtooth: `t` runs 0 → 1 → 0 across the
loop, so the repeat has no seam. A banner that snaps back every two seconds
reads as a broken GIF.

`outElastic` was one of the four and is not any more. Its oscillation is dense
enough at this width to read as a rendering glitch rather than as a curve, which
is a fact about the drawing rather than about the curve.

## Why four files rather than two

GitHub honours `<picture>` and `prefers-color-scheme`. **npm and crates.io strip
`<source>`** and render the `<img>`, so whatever that points at is what a
package page shows — hence one theme-neutral file, neutral meaning it reads on a
white page and on a dark one. That rules out a near-white or a near-black field,
which is why it is a mid-slate rather than either end of the range.

## Two things to know before regenerating

**No font is registered, so it draws with what the host has.** The committed
files were rendered on macOS; regenerating on another machine will set the type
differently. That is a property of the picture rather than a defect, but it
means a regeneration is a visible diff and should be looked at rather than
committed blind.

**The READMEs link these by absolute URL on the `v10` branch**, because a
relative path is a dead end on npm and crates.io — their tarballs carry the
README and nothing else from this directory. When `v10` becomes the default
branch, those URLs need updating to match.

## Cost

The reason these are in git rather than LFS is that they are small: the animated
files are about 170–180 KiB each, and README images are fetched on every package
page view, which is metered bandwidth on LFS. If a change to this drawing pushes
the animated files much past half a megabyte, cut frames or duration rather than
committing it.
